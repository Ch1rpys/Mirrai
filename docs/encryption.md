# 数据库静态加密（C8.5）

Mirrai 可以把数据库里的文字存成密文：只有登录之后，服务进程手里有这把数据密钥时，才读得出来。这一页写清楚加密了什么、没加密什么、怎么开、开完会发生什么、丢了钥匙会怎样。

## 范围

**加密的列**（每个账号一把 32 字节的数据密钥，AES-256-GCM，每个值自己的 nonce）：

| 表 | 列 |
|---|---|
| `messages` | `content` |
| `memories` | `title`、`description` |
| `letters` | `body`、`replyText` |
| `outbound_letters` | `text`、`outcomeNote` |
| `user_journal` | `body` |
| `diary_entries` | `summary`、`reflection`、`highlights`、`quotes`、`emotionalArc` |
| `collected_messages` | `content`、`meta` |
| `personas` | `personaData`、`styleProfile` |
| `persona_versions` | `personaData`、`styleProfile` |
| `rehearsals` | `line`、`result` |
| `roleplay_sessions` | `transcript` |
| `scheduled_items` | `body` |
| `oral_accounts` | `body` |

`collected_messages.meta` 里的 `register`（`private` / `public` / `written` / `group`）是一个例外：它同时明文复制在 JSON 顶层，因为按场合筛选的 SQL 直接读 `meta->>'register'`。`register` 只有四个固定取值，不含内容；`meta` 的其余部分（转录、路径、标签等）在密文里。

**不加密**：

- 上传目录里的照片、录音、视频、导出包——这些文件不在加密范围内。**建议把数据目录放在系统级加密的磁盘上。**（备份文件本身可以另设口令加密，见 `docs/backup.md`。）
- 不在上表里的表：例如聊天摘要、安全事件、蒸馏卡片、`personas.farewellLetter` 等。这一阶段只覆盖手册列出的列；如果以后要扩，按同一套方法加列（`server/_core/encrypted-values.ts` 的 `ENCRYPTED_TABLES` 是唯一清单，迁移任务和验收测试都读它）。

## 钥匙怎么放

- 每个账号一把数据密钥，随机 32 字节。
- 它用**登录密码**派生的密钥（scrypt，N = 2^15、r = 8、p = 1）包起来，存在 `users.encryption` 里。数据密钥本身从不落盘。
- 启用时另外生成一个**恢复码**（6 组 4 位字符），用同一把数据密钥的另一份包装存下来。恢复码**只显示这一次**，应用不保存明文。
- 登录时，服务端在验证密码通过的那一刻解开数据密钥，放在**进程内存**里（闲置 24 小时、显式上锁、改密码、进程退出都会清掉）。它不会回到浏览器。
- 改密码时用新盐把同一把数据密钥重新包一遍；数据密钥本身不变（换钥匙就要重加密整个库）。
- 用恢复码可以重设密码：解开数据密钥、用新密码重新包。

## 开启

设置 → 数据 → 「加密存在数据库里的内容」。

1. **先下载一次完整备份。** 没有备份记录时服务端拒绝开启。原因是：如果密码和恢复码一起丢了，那份备份是唯一的退路。
2. 输入账号密码，勾选两条后果（内容丢失风险、重启后要重新登录才继续后台任务）。
3. 服务端生成密钥、恢复码，然后开始**后台任务**：每批 500 行把已有的行加密，进度写在 `users.encryption.migration` 里，页面上能看到。
4. 把恢复码抄下来，放在别处。

后台任务可以中断、可以续跑：进程停了，下一次调度器 tick 会在账号解锁的情况下继续；没解锁就等下一次登录。任务跑完之前，**旧行是明文、新行是密文**，读取两种都正确。

## 开启之后

- 重启服务之后，会话 cookie 仍然有效，但内存里没有钥匙：所有数据请求返回 `ENCRYPTION_LOCKED`，界面弹出输入账号密码解锁的窗口（输入一次就恢复）。
- 加密账号的后台任务（晚点回、回信、主动开口、到期胶囊、定时备份、加密迁移本身）在没解锁时**顺延到下一次登录**，调度器只记一行日志，不报错。
- 搜索：加密账号的 `searchTokens` 不再存明文字二元组，而是每个二元组的 HMAC（前 16 个十六进制字符），查询时对查询串做同样的变换。所以：
  - 加密账号的搜索**至少两个字符**；单字查询没有二元组可查，返回空。
  - 逐条记录和聊天的全文搜索走盲索引；回看类功能里按内容包含的二次确认在解密之后做。
  - 「记忆」「日记」这类没有索引列的表，在加密账号上由应用层读出来再过滤（行数少，可以接受）。
  - 开启任务没跑完的行不在索引里；跑完之后旧记录才能搜到。

## 关闭

同一面板的「关闭加密」要账号密码。它跑同一套后台任务，方向反过来：把密文解密、索引换回明文二元组，全部写回明文之后把 `users.encryption` 清空、忘掉钥匙。行数不变。

## 备份与还原

- 备份导出的是数据库的**原样**：加密账号的行是密文，`users.encryption` 的包装一起在备份里。
- 还原到一个全新的空实例后，用**原来的账号密码**登录即可：钥匙在 `users.encryption` 里，密码能把它解开。
- 如果换机器后要开启加密，需要先下载一次完整备份（见上）。
- 上传目录的文件不在加密范围内，见 `docs/backup.md`。

## 已知边界

- **家庭共用（C7.2）**：一个加密账号把分身分享给别人时，分身身份字段在成员自己那行里有一份「接受邀请时」的副本（按成员的钥匙加密）。成员实时读到的主人行内容需要主人在这台实例上登录过（主人的钥匙在进程内存里）；没有时成员看到副本，且主人的规则更新不会即时反映。这一条没有专门的界面提示。
- 如果一行明文恰好以 `enc:v1:` 开头（用户自己打出这种句子），开启加密时它会被当成密文跳过，之后读取会失败。这个碰撞实际上不会发生，但它是格式没有转义带来的边界。
- 恢复码和密码都丢了：没有找回的办法。这是加密的定义，不是缺陷。

## 相关代码

- `server/_core/content-crypto.ts`：密钥包装、内容加解密、恢复码、盲索引 HMAC。
- `server/_core/data-keys.ts`：进程内存里的数据密钥。
- `server/_core/encrypted-values.ts`：加密列清单、状态缓存、读写的透明变换。
- `server/encryption/migrate.ts`：分批启用/停用任务。
- `server/encryption/enable.ts`：开启、关闭、恢复码重设密码。
- `server/encryption/lock.ts`：后台任务在未解锁时跳过。
- `server/routers-v6/encryption.ts`：`encryption.status/unlock/lock/enable/disable/recover`。
- `docs/backup.md`：完整备份与还原。
